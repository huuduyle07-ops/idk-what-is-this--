# Frozen lifecycle consumer and state-machine audit

This is source and frozen-test analysis for `SYNTH.AUTH.LIFECYCLE.PINNED.COMPAT.1`, dated 2026-10-11 KST. No authorization, execution lease, provider, runtime, reflection, replay or transition was invoked to produce this trace. Existing source, tests, receipts and historical lifecycle policies are unchanged.

The source supports `LIFECYCLE_PINNED_REQUIRES_ADDITIVE_ADAPTER`. The one-shot state-machine rules are reusable unchanged, but the frozen public implementation authenticates only `SYNTH.AUTH.1`. Its public API cannot truthfully accept a pinned authorization, even if every scenario field matches. An additive binding would need its own truthful owner boundary; this audit implements none.

## Provider distinction and preserved policy caveat

The lease dataclass and lifecycle executable authentication/transition code do not inspect provider-root identity, provider proof, requirement schema, Docker, Java binary or infrastructure readiness. They authenticate an old upstream object and bind its ID/fingerprint to the exact scenario. Old Java requirement validation is consequently transitive through the old public validator, not an independent lifecycle provider algorithm.

The literal `JAVA.1` in `CONSUMPTION_POLICY` (`core/synthetic_runtime_authorization_lifecycle.py:38-42`) is classified `OLD_JAVA_REQUIREMENT`: it is an explicit, frozen historical requirement for a future executor's activation boundary. The old documentation states that boundary (`docs/roadmap/phases/SYNTH_AUTH_LIFECYCLE_1/SYNTH_AUTH_LIFECYCLE_1.md:79-96`); a frozen pure test asserts the literal `SANDBOX.2` and `JAVA.1` (`tests/test_synthetic_runtime_authorization_lifecycle.py:457-463`). Treating this policy as interchangeable with a pinned requirement would reinterpret frozen history. It has no executable independent provider test in the lifecycle owner and is not evidence that the epoch-independent terminal state rules change. A future additive owner must state its new authenticated provider/precondition binding truthfully, without editing the old policy or declaring the old API pinned-compatible.

Likewise `COMPILATION_POLICY` (`core/synthetic_runtime_authorization_lifecycle.py:43-47`) preserves zero compilation authority and requires reporting any future conflict over whether compilation is runtime activation. This is a preserved scope/activation constraint (`SEMANTIC_SCENARIO_REQUIREMENT`), not permission to compile.

## Frozen-test evidence and zero-effect selection

The frozen lifecycle suite calls real process-local owner APIs: `_auth()` at `tests/test_synthetic_runtime_authorization_lifecycle.py:41-43`, `_pair()` at lines 46-48, and `_consume()` at lines 51-54. Its no-runtime-effects fixture at lines 27-32 does not forbid authorization/lease issuance or pure consumption. Therefore running the full suite here would violate the user-required zero issuance/consumption even though those tests launch no Java/runtime.

The tests cited above were read, not executed by this source audit. The policy-only frozen test `test_future_consumption_boundary_is_explicit_and_has_no_runtime_implementation` at lines 457-463 is safe to run unchanged because it reads constants. Strict-proof and replay tests at lines 465-504 are excluded because they invoke `verify()` or `replay()` and issue a pair. New focused fixture analysis should use inert old/pinned projections or source contracts, with no production validator weakening and no lease issuance/consumption path.

Implementation API reuse result: **false** for pinned upstream objects. Semantic one-shot state-machine reuse result: **true**, subject to a truthful additive authorization/lease binding. This trace claims no reflection compatibility and implements no adapter, lease owner, provider or executor.
