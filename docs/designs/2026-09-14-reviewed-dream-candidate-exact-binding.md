# AUTH.DREAM.1 — Reviewed Candidate Exact Binding for Dream Apply

Implemented 2026-09-14. This phase addresses AUTH-01 only. The exact reviewed candidate is re-resolved from named server artifacts and checked against its repository, run, item, executable content and artifact bytes before the existing Dream execution path. Creating another run cannot substitute its candidate. DATA-02 is not implemented.

1. **Exact files changed.** Eight existing files changed and seven files were added; the complete list is below. The entry capture contains 1,465 files, including pre-existing uncommitted and untracked work. Eight contextual reversals reconstruct the exact entry bytes. No files were staged and no commits were created in the working repository. No stash, reset or clean was used.
2. **Old flow.** `applyDream()` fetched `/dream/list`, displayed items from run A, and posted only `repo_path` and numeric `selection`. `/dream/apply` independently called `latest_report_dir`, then loaded that report's item and `patch_plan.json`. A later run B could take A's place.
3. **Root identity bug.** An index within a report was treated as candidate identity across reports. The manual-Apply telemetry described execution authority without binding it to the report the user had reviewed.
4. **Binding owner.** `core/dream_review_binding.py` owns the immutable contract, offered review snapshots, exact lookup, executable fingerprint, artifact commitment, typed transport validation and closed review failures. Neither the normal Apply authority owner nor the executor was rewritten.
5. **Binding schema.** Frozen `DreamReviewedCandidateBinding` contains `schema_version`, `repository_id`, `run_key`, `item_idx`, `candidate_fingerprint` and `artifact_fingerprint`. The schema is `dream_reviewed_candidate_v1`. Transport requires exactly these fields; booleans are not integer item IDs, fingerprints must be lowercase SHA-256 values, and run keys must match the existing bounded layout. `ResolvedDreamCandidate` retains immutable item JSON and plan bytes; accessing the plan returns a new parsed copy.
6. **Repository identity.** `core.repository_identity.build_repository_identity` supplies the existing canonical physical root and repository ID. Its established symlink/case policy is reused. The server computes it from the request context, cross-checks the binding and executes against the canonical root. No cwd, basename, project tag or client path string becomes identity. Existing path-derived identity does not detect wholesale replacement of a repository at an unchanged canonical path.
7. **Run/report identity.** The existing `date/run` key, including the run directory's collision suffix, locates one report. Legacy `date` keys can be freshly rebound when sufficient artifacts exist. Identity is the exact key together with the server-recomputed artifact commitment; a timestamp alone never authorizes Apply. No new run database, UUID or global current-run state was introduced.
8. **Item identity.** The exact report's integer `idx` locates exactly one item. Missing items and duplicate indices fail closed. The artifact commitment also covers `item_idx` and the stored `item_dir_name`, so equal payloads at different item locations do not erase provenance.
9. **Candidate content fingerprint.** SHA-256 of canonical JSON, with sorted object keys, preserved array order, compact separators and exact string values. It binds the operation payload actually passed to execution, plus the item's `kind` and `status` capability discriminators. It is independent of the report key, so identical candidates in different runs may share this content fingerprint.
10. **Fingerprinted executable fields.** Ordered plan operations include `op`, `relative_path`, `file`, `content`, `target_snippet` and `patched_snippet` when present. Raw path aliases and missing-versus-present fields remain distinguishable. This is a conservative projection of every field inspected by the existing executor's schema/path/payload preparation. Unknown metadata keys, titles and summaries are excluded from the executable digest. They cannot authorize a transformation. A separate artifact commitment covers exact `list.json` bytes, the chosen displayed summary's filename and bytes, exact selected `patch_plan.json` bytes or absence, canonical repository ID, run key, item index and item directory. Thus even whitespace/metadata-only edits to these reviewed artifacts require review again. Supporting research, case ideas and refinement-analysis files are non-executable and are not part of this commitment.
11. **Review-binding creation moment.** The server offers a bounded identity with the report snapshot. This is not approval. The browser binds a candidate only when the human checks its checkbox or explicitly chooses Select all in the Apply dialog. Generation, polling, listing and opening the dialog leave the selected binding null. The dialog displays the captured executable plan in an open `Patch to apply` detail before selection. The historical report viewer also displays that exact payload; its navigation does not itself select items for Apply.
12. **UI transport.** Each checkbox retains an immutable copy of its offered binding and a separate selected binding. Apply sends the selected bindings as JSON in `review_bindings`, alongside the existing repository and selection fields. No browser hashing, general frontend store or session persistence was introduced. New run/sidebar updates cannot change the dialog's controls. Opening a fresh Apply dialog explicitly establishes a new review context and starts unselected.
13. **Server lookup.** Apply parses the complete selected binding list, verifies the selection cross-check and resolves every selected item before any execution. For each item it uses only the named report, list, displayed summary and selected plan. Repository identity is recomputed. A second resolution occurs after existing repository-inventory/validation-command selection and immediately before mutation observation/lifecycle entry.
14. **Latest fallback removal.** `/dream/apply` has no latest-report lookup or fallback. `selection=all` means exactly the transported, explicitly selected bindings, never all items from a current report. Latest remains only in existing navigation/display paths. A regression replaces `latest_report_dir` with a throwing spy during Apply and still executes A successfully.
15. **Authoritative candidate revalidation.** Server-stored bytes are parsed and fingerprinted again, compared with the supplied identity, and passed as the verified in-memory plan to the unchanged gates/lifecycle. Browser-supplied patch content is ignored. There is no post-review candidate generation or refinement. Preferred refinement metadata cannot redirect execution; the displayed and executed payload remains the selected item's original `patch_plan.json`. Existing executor path normalization, snippet/newline semantics and dynamic repository validation remain their frozen contracts.
16. **Repository mismatch.** A binding reviewed in repository A is rejected in B with `reviewed_repository_mismatch` before artifact execution or mutation. The fixture uses two distinct physical repositories, including identical repository basenames in the direct test.
17. **Run mismatch.** A nonexistent key returns `reviewed_run_not_found`. A different existing run returns `reviewed_candidate_changed` when payloads differ or `reviewed_artifact_stale` when content matches but report provenance differs. Malformed/traversal keys return `review_binding_required`.
18. **Item mismatch.** An absent index returns `reviewed_candidate_not_found`; duplicate indices invalidate the artifact. Selection disagreeing with the binding list returns `review_binding_required`. There is no fallback to another index or run.
19. **Fingerprint mismatch.** `reviewed_candidate_changed`, `review_required=true`, no execution and no repository mutation. Each executable field has a fingerprint regression; changed operation order and exact text are preserved by the ordered canonical payload.
20. **Artifact change.** Rewriting `list.json`, changing titles or displayed summary, changing plan whitespace, deleting/changing the plan, editing capabilities or replacing malformed JSON is refused. Candidate changes use the candidate error; other commitment changes use `reviewed_artifact_stale`. Byte-identical replacement preserves content identity. This is not an inode/mtime attestation. There is no cross-process artifact lock: edits after the final check cannot substitute different bytes into the captured payload; subsequent requests must revalidate again.
21. **Missing artifact.** Missing report/list returns structured `reviewed_run_not_found`; a previously present plan becoming absent invalidates the candidate. Unreadable or malformed artifacts return `reviewed_artifact_stale`. A review that already represented absence of a plan remains subject to the existing `skipped_no_plan` gate, with no execution.
22. **Legacy artifact behavior.** Old unbound requests always fail closed. A legacy report can remain viewable and obtain a fresh binding only through the new report/review snapshot path when its exact item directory and UTF-8 JSON plan can be resolved. Explicit selection and manual Apply are still required. Insufficient, ambiguous, non-list or non-UTF-8 stored executable representations remain viewable without a binding. Stored fields purporting to be review bindings are stripped and never trusted.
23. **Run-A/Run-B regression.** The PRE test compiles the exact captured entry route and executes it through the real Flask request and current unchanged lifecycle/executor: A/item1 is listed, B/item1 is created, numeric Apply writes `unreviewed.txt`. POST repeats the sequence with A's transported binding and writes only `reviewed.txt`, with exact CRLF payload bytes. No model is needed. Chromium separately exercises the production dialog, actual checkbox selection, later B creation and real Flask Apply.
24. **Same selection/different run.** A and B both use index 1; their different executable payloads have different candidate digests and their report keys differ. B cannot satisfy A's binding.
25. **Same content/different run.** Equal executable fingerprints are permitted. The run key is included in the artifact commitment, so changing A's locator to B while retaining A's binding is refused even when the report and plan bytes match.
26. **Repository-switch regression.** Direct owner, HTTP and browser tests switch the request/UI repository after selecting A. All refuse before mutation. The browser clears/disables the invalid selection and shows the review-again message.
27. **Exact successful Apply result.** A's response identifies A's title and index, reports `applied`, and the real executor writes A's exact marker bytes. B's marker is absent. Existing post-Apply Git behavior is unchanged. Fixtures live under the ignored `.tmp` tree; Git staging is refused there, while successful patch application is still reported separately from commit failure. The tests assert candidate bytes and receipt identity, and introduce no new commit contract.
28. **Successful receipt identity.** `dream_review_receipt` contains `identity_verified=true`, `reviewed`, `resolved` and `executed`. Successful execution has identical binding records in all three identity slots. The existing lifecycle also persists the reviewed/resolved binding inside `control_result.json` before execution, beside the actual persisted plan and normal replay outcome. The HTTP receipt makes reviewed versus executed identity directly comparable without changing the lifecycle owner.
29. **Failure receipt identity.** Failures before the binding gate return closed errors and the established `no_execution(candidate_mismatch)` telemetry. They contain no fabricated Dream execution receipt. Validly resolved items refused by later capability/path gates may retain a verified review receipt with `executed=null`.
30. **Execution-attempt semantics.** `execution_attempted`, `mutation_observed`, `patch_applied` and `final_repository_changed` are false on binding failures. Later executor results keep the established telemetry vocabulary and semantics. `executed` is populated only when that existing telemetry says execution was attempted; this phase does not reinterpret generic rollback or recovery truthfulness.
31. **Plan-only rights delta.** Zero. Idea and research items are still skipped. Every existing plan-only status is still skipped, other non-ready statuses stay blocked, and no-plan items remain unexecuted. Tests deliberately place write-shaped plans behind all these restrictions and prove the executor is not called. Changing a stored plan-only capability after review invalidates the binding.
32. **Main coding Apply delta.** Zero. No changes to `core/human_apply_authorization.py`, candidate eligibility/approval/freshness owners, `/apply_patch`, or `web/routes/patch_routes.py`. Relevant normal Apply tests ran.
33. **EXEC.PLAN.1 delta.** Zero production/semantic delta. Plan preparation, transaction execution/recovery and transaction-local receipt fields remain entry-identical. Its test-only historical reader now removes AUTH.DREAM.1 changes before applying the existing immutable reversal receipt.
34. **DATA.UNDO.1 delta.** Zero. No durable Dream backup producer, new Undo receipt, restore path or consumption change. Existing Undo source, routes and browser transport remain unchanged outside the specifically isolated Dream template/app edits.
35. **DATA-02 delta.** Zero. Generic rollback truthfulness remains open. No harmonization of receipt booleans or validation-side-effect guarantees was attempted.
36. **SEC.UI.1 delta.** Zero sanitizer-policy delta. Safe-content code and vendored dependencies are unchanged. New executable payload text uses the existing HTML escaping boundary. Existing report Markdown rendering remains in place, and the frozen Chromium security tests ran.
37. **Track-A delta.** Zero semantics. Pipeline, main executor, live task routing, candidate verification, lifecycle and validation owners remain entry-identical. The existing recorded frozen T6 lifecycle case ran; T6 Round 11 was not started.
38. **Reload/session behavior.** Existing Dream review selection was ephemeral. The exact binding remains ephemeral on the current modal's controls. Reload or reopening the dialog requires new selection; no session/local-storage inference from latest is possible. Browser reload and explicit-new-review tests pin this transition.
39. **Replay behavior.** No one-shot consumption was introduced. The same reviewed binding can be validated again. A second create-file Apply is refused by the existing file-exists executor precondition, not by a newly invented approval-consumption rule. No stored Dream metadata is updated by the binding owner.
40. **Structured errors.** Closed codes: `review_binding_required`, `reviewed_run_not_found`, `reviewed_candidate_not_found`, `reviewed_candidate_changed`, `reviewed_repository_mismatch`, `reviewed_artifact_stale`. They include `success=false`, `review_required=true`, an error/message requiring re-review and no-execution telemetry. Both request-wide and per-item late-check failures are visible in the UI.
41. **Model/network.** Zero live provider calls and zero external network requests. Frozen artifacts, provider adapters in adjacent tests, real local executors and locally intercepted Chromium requests are used. The global validation network guard recorded zero external attempts. No dependency downloads/installations were performed. The unrelated existing graph CDN is intercepted in new browser tests rather than contacted.
42. **Traversal.** The binding owner adds no repository or Dream-corpus walk. It inspects only the specified artifact path chain and named files. Report/item/plan symlinks and Windows junctions are rejected below the configured Dream storage root, including a real junction regression. UI listing and existing inventory/lifecycle/validation traversal remain unchanged; this is not a claim that the entire old Apply path never traverses repositories.
43. **Performance.** Bounded local measurements of exact report lookup, candidate byte loading/fingerprinting, canonical repository identity, typed binding validation and full resolution are recorded below. No corpus benchmark. Measurements use 31 samples after five warmups with no competing test runs. Rows overlap and must not be summed; the Apply route resolves before the batch and again before execution.

The existing unsafe-path Dream test now obtains a real binding before asserting its unchanged safety gate. Tests cover unselected opening, explicit checkbox/Select all, A surviving B arrival, exact request transport, tamper refusal before and during Apply, repository switch, reload and a new explicit review. All 54 benchmark metadata checks, compileall for core/patching/web/tests and git diff --check pass. The final metadata/frozen-attribution follow-up passed 273 cases. Across focused, broad and follow-up results there are 1,394 unique passes, two platform-specific skips and zero unresolved failures. Only AUTH.DREAM.1 was appended in the existing HARDEN track. Earlier phase entries and their completion claims were not rewritten. The prior entry's unrelated EXEC.PLAN.1 summary text was preserved, rather than silently corrected in this phase.
48. **Frozen/concurrent attribution.** The entry manifest captures 1,465 source/test/doc/config files, including the user's existing dirty state. Eight known edits reverse byte-for-byte; original audits, old frozen/completion/reversal fixtures and production frozen owners are unchanged. New phase evidence is stored separately. 50. **AUTH-01 closure.** Closed for the audited Dream Apply path: only the exact candidate represented by a complete reviewed binding can cross the identity gate. Later runs cannot retarget an older review; missing, stale, mismatched or legacy unbound requests fail closed; successful receipts identify the same reviewed and executed candidate. Exact binding remains necessary but insufficient for execution: human Apply and all existing capability, path, plan and validation gates still apply.
